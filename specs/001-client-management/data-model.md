# Client Data Model

## Existing persisted entity

### Client

Represents a person registered by one tenant. The existing Prisma model remains unchanged.

| Field | Existing shape | Feature use and validation |
|---|---|---|
| `id` | String primary key, generated by Prisma | Used to identify a client for edit/delete; validated as a non-empty identifier. |
| `tenantId` | Required string, indexed; tenant relation | Derived only from the authenticated server session. Never accepted as trusted mutation input. |
| `name` | Required string | Required and trimmed; empty values are rejected. |
| `email` | Optional string | Optional; when present, must be a valid email address. |
| `phone` | Optional string | Optional contact text; retain as text to preserve formatting such as `+`, spaces, and punctuation. |
| `createdAt` | Required timestamp, defaulted by Prisma | Persistence metadata; available for listing/ordering only if needed by the established UI pattern. |
| `updatedAt` | Required timestamp, updated by Prisma | Persistence metadata; not user-editable. |

## Relationships and deletion behavior

- Client belongs to one Tenant through `tenantId`; every feature operation is constrained
  to the tenant from the authenticated session.
- Existing Appointment and Ficha records refer to Client and restrict deletion. The CRUD
  does not manage these relationships. A failed delete preserves the client and dependent
  records and returns an actionable error.
- The UI does not expose appointments, professionals, services, fichas, or other
  relationship data as part of this feature.

## List view and query contract

The list projection contains the identifier, name, email, and phone required for display
and row actions. The query accepts:

- `search`: trimmed text, maximum 100 characters; partial case-insensitive match against
  name, email, or phone.
- `page`: positive, 1-based integer, defaulting to `1`.
- `pageSize`: positive integer, defaulting to `10`; cap at `100`.
- `sortBy`: allowlisted name, email, or phone field; default `name`.
- `sortDirection`: `asc` or `desc`; default `asc`.

The result contains `items`, `total`, `page`, `pageSize`, and `pageCount`. All filtering,
counting, ordering, and pagination are tenant-scoped. Append `id` as a stable unique
tie-breaker to the requested ordering so page boundaries remain deterministic.

The client query cache includes all list parameters, following the existing Service list
pattern. The cache is a UI optimization only; it does not authorize or scope server
operations.

## Mutation rules

- Create accepts `name`, optional `email`, and optional `phone`; tenant is injected by the
  server and not part of the trusted client input.
- Update accepts a non-empty client identifier and the same editable fields. The update
  predicate includes both client ID and authenticated tenant ID.
- Delete accepts a non-empty client identifier. The delete predicate includes both client
  ID and authenticated tenant ID.
- Email and phone are not unique unless a separate requirement establishes that constraint.
- No schema migration is required for this feature.
